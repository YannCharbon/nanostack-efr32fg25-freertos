# nanostack-efr32fg25-freertos

Experimental proof-of-concept firmware for the Silicon Labs **EFR32FG25**. It
runs our extracted Nanostack
([`nanostack-generic-standalone`](../nanostack-generic-standalone), Wi-SUN FAN 1.0
profile) on **FreeRTOS** with a **RAIL** radio driver, as two images, for two
board/region variants:

| Variant (CMake preset) | Radio board, mainboard | Wi-SUN PHY | Status |
| --- | --- | --- | --- |
| `fw` (default): `FW_BOARD=brd4271a`, `FW_REGION=EU` | BRD4271A (863–870 MHz) on BRD4001A | EU, operating class 1 (863.1 MHz + n×100 kHz, 69 channels), PHY mode 1a (50 kbit/s 2-FSK, h = 0.5) | **two-board network verified on hardware** (3 cold boots) |
| `fw-na`: `FW_BOARD=brd4270b`, `FW_REGION=NA` | BRD4270B (902–928 MHz) on BRD4002A | NA, operating class 1 (902.2 MHz + n×200 kHz, 129 channels), PHY mode 1b (50 kbit/s 2-FSK, h = 1.0) | builds; host twin only, not run on hardware |

The two images:

| Image | Role | Nanostack config |
| --- | --- | --- |
| `wisun_br` | Border Router: authenticator (EAP-TLS server), DHCPv6 server, RPL root, null backhaul with static prefix `fd12:3456::/64` | `ws_border_router` |
| `wisun_rn` | Router Node: EAP-TLS supplicant, DHCPv6 client, RPL router, UDP test on port 1234 | `ws_router` |

The specification is section 5 of
`nanostack-generic-standalone/docs/GENERICITY_PLAN.md`. Deviations from it are
listed in [Design notes](#design-notes). This firmware is the reference port
of the stack's porting guide, `nanostack-generic-standalone/docs/PORTING.md`:
`port/freertos/` implements the porting API and `drivers/rail/` the radio
driver.

**Status (2026-10-23).**

- Both images build headless, for both variants, and link against the real SDK,
  FreeRTOS and RAIL library.
- **On two BRD4271A kits (EU), the BR and the RN form a valid Wi-SUN network.**
  The RN authenticates with EAP-TLS, installs the GTK, picks the BR as RPL
  parent and gets a DHCPv6 address in `fd12:3456::/64`; the BR lists it in its
  routing table. Ping and UDP work both ways. This held on 3 consecutive cold
  boots; see [Hardware results](#hardware-results-brd4271a-eu-2026-10-23).
- The same application, port and driver code also runs in a **host twin** on
  Linux with a fake RAIL; see
  [Host twin](#host-twin-sanity-check-without-hardware).
- Not run on hardware: the NA/BRD4270B variant, more than two nodes, long runs.

## Build

```bash
cmake --preset fw                # BRD4271A / EU (default): configure once (build/fw, toolchain file, Ninja)
cmake --build --preset br        # -> build/fw/wisun_br.{elf,hex,s37,bin,map}
cmake --build --preset rn        # -> build/fw/wisun_rn.{elf,hex,s37,bin,map}
cmake --build --preset all       # both

cmake --preset fw-na             # BRD4270B / NA variant (build/fw-na)
cmake --build --preset br-na     # or rn-na / all-na

cmake --preset fw-mode3          # BRD4271A / EU, PHY mode 3 (build/fw-mode3)
cmake --build --preset all-mode3 # or br-mode3 / rn-mode3
```

`FW_BOARD` and `FW_REGION` can also be set by hand. Configure fails if the
region does not match the board, because each generated radio config is
single-band.

**PHY mode (`FW_PHY_MODE`).** EU has two modes; NA has 1b only.

| `FW_PHY_MODE` | Wi-SUN (FAN 1.0) | Channels | Radio config |
| --- | --- | --- | --- |
| `1a` (EU default) | operating class 1, mode 1a: 2-FSK 50 kbit/s, h = 0.5 | 863.1 MHz + n × 100 kHz, 69 | `sdk/gen/brd4271a` |
| `3` | operating class 2, mode 3: 2-FSK 150 kbit/s, h = 0.5 (the emulator's default) | 863.1 MHz + n × 200 kHz, 35 | `sdk/gen/brd4271a-mode3` |

Mode 1a stays the default. Mode 3 sets the stack's class and mode
(`apps/common/app_config.h`), the driver's data rate (150 kbit/s) and its CCA
length (8 symbols, 53 µs) (`drivers/rail/rail_phy_config.h`). The 1a images are
byte-identical with and without this option. Both nodes of a network must use
the same mode.

**Event-loop idle-tick skipping and the run-loop safety timeout.** The stack's
option `NANOSTACK_EVENTLOOP_SKIP_IDLE_TICKS` (default ON) arms the 10 ms tick
only when an event timer is due. `FW_RUNLOOP_SAFETY_MS` is the longest wait of
the run loop without a notification; see [Design notes](#design-notes) for the
default and the hardware check behind it.

Other paths: `cmake --preset fw -DNANOSTACK_DIR=... -DSISDK_DIR=... -DMBEDTLS_DIR=...`.
Configuration knobs (`apps/common/app_config.h`, `drivers/rail/rail_phy_config.h`)
take `-DAPP_EXTRA_DEFS="NAME=value;..."` (apps). Driver values are edited in
the header or passed with `-DCMAKE_C_FLAGS_MINSIZEREL="-Os -g -DNAME=value"`.
Do not use `-DCMAKE_C_FLAGS=-D...`: it replaces the toolchain's CPU flags and
the link fails.

A clean build of both images takes about 4 s on 16 cores. Each link prints a
size report and **fails if** flash > 1 MB or static RAM without the heap > 64 kB
(`tools/size_report.py`).

### Image sizes (EFR32FG25B222F1920IM56: 1920 kB flash, 512 kB RAM)

Same for both variants, within 0.1 kB:

| | `wisun_br` | `wisun_rn` |
| --- | ---: | ---: |
| Flash (text + rodata + data init) | **552.4 kB** (28.8 %) | **502.2 kB** (26.2 %) |
| Static RAM, total | 259.8 kB (50.7 %) | 259.3 kB (50.7 %) |
| – of which FreeRTOS heap_4 (`configTOTAL_HEAP_SIZE`, the stack's malloc pool) | 200.0 kB | 200.0 kB |
| – of which everything else | 59.8 kB | 59.3 kB |
| RAM left unused | ~252 kB | ~253 kB |

Two changes made on hardware account for about 35 kB of flash: full newlib
instead of newlib-nano (see
[Hardware results](#hardware-results-brd4271a-eu-2026-10-23)), and DEBUG-level
traces compiled in. The breakdown below was measured before those changes.

Per-component breakdown (`python3 tools/map_breakdown.py build/fw/wisun_br.map`), BR flash:

- RAIL library 123 kB; Wi-SUN (`6lowpan/ws`) 64 kB; mbedTLS 62.5 kB.
- SDK platform 56 kB; MAC/FHSS/CCM 32 kB; security 28.6 kB.
- Other stack code 26 kB; IPv6/ICMP/UDP/TCP 25 kB; RPL 24 kB; 6LoWPAN 20 kB.
- libc 14.5 kB; FreeRTOS 11 kB; DHCPv6 11 kB; apps 5.4 kB; driver 3 kB; port 2.4 kB.

The RAM outside the heap is mainly:

- RAIL 19 kB;
- driver FIFOs and RX ring 18 kB;
- port 10 kB (8 kB trace ring);
- mbedTLS 8.6 kB;
- stack-task stack 8 kB.

Peak heap: about 58 kB in the host twin, and on hardware 46 kB on the BR and
40 kB on the RN with one node (`heap` CLI command, "min-ever free" 158.5 kB and
165 kB of 200 kB).

`slc generate` ran the Radio Configurator headless on Linux (Radio
Configurator 2502.6.4). The SDK component `radio_config_brd_wisun_singlephy`
picks the configuration from the board:

- BRD4271A: `PHY_WISUN_FAN_1v1_863MHz_Plan32_2FSK_1a_EU`. Channel plan 32 is
  EU 863.1 MHz / 100 kHz, RAIL channels 256–324.
- BRD4270B: `PHY_WISUN_FAN_1v1_915MHz_Plan1_2FSK_1b_NA`, RAIL channels 512–640.
- BRD4271A, mode 3: the component has no mode 3 configuration for this board,
  so `sdk_generate.sh brd4271a-mode3` switches the generated
  `radio_settings.radioconf` to the SDK's `PHY_WISUN_FAN_1v1_863MHz_Plan33_2FSK_3_EU`
  (channel plan 33: EU 863.1 MHz / 200 kHz, 35 channels; RAIL channels 0–34) and
  generates again. Only the radio config files differ from `sdk/gen/brd4271a`.

So the plan's fallback (generate it in Simplicity Studio) was not needed.

## Host twin (sanity check without hardware)

`tests/host_twin/` builds the firmware's own files, unchanged:

- `apps/`;
- `port/freertos/`;
- `drivers/rail/rail_phy.c`;
- the same Nanostack and mbedTLS sources and configuration.

They are built for Linux, with three host replacements:

- a pthread implementation of the FreeRTOS subset used;
- a **fake RAIL** (`fake_rail.c`), compiled against the real SDK RAIL headers. Node processes exchange frames over UNIX datagram sockets. The model includes 50 kbit/s air time, channels (RX only on the tuned channel), collisions, CCA and scheduled TX;
- stub SDK services: VCOM to stdio, SE TRNG to `getrandom`, DEVINFO EUI-64 from the node index.

```bash
cmake -S tests/host_twin -B build/host -G Ninja && ninja -C build/host
tests/host_twin/run_twin.sh build/host            # BR + RN, scripted through the real CLI, ~4 min
```

What it exercises:

- the §3.3 init sequence and in-process MAC wiring;
- the port (critical sections against concurrent "ISR" threads, timers, notifications, heap wrap);
- the driver state machine (CCA_PREPARE, scheduled CCA/TX, RESTART_CSMA, abort, channel changes, RX ring, Enh-ACK path, PHR building);
- EAP-TLS with the target mbedTLS config;
- DHCPv6, RPL, the BBR routing table, ICMPv6 and UDP.

It does **not** exercise:

- RAIL itself, real RF timing, CCA physics or SDK init;
- ISR priorities, stack sizes or tickless/EM modes.

Two other differences:

- The host build defines `__linux__`, and the stack has a few
  `#ifdef __linux__` blocks: traces, `whiteboard_os_modify`, and FHSS drift
  compensation in `rcp/fhss/fhss_ws.c:1176` (on the target only).
- `rail_config.c` cannot be compiled for a 64-bit host, so the fake RAIL
  copies its channel range.

Results (3 consecutive runs, final code, 60 s settle before the tests):

| Run | RN join | Auth / GTK / parent / GUA / `nodes` | UDP both ways | Ping RN→BR | Ping BR→RN | Enh-ACK latency max (RN / BR) |
| --- | ---: | --- | --- | ---: | ---: | --- |
| 1 | 114 s | pass | pass | 6/10 | 6/10 | 3.7 / 3.6 ms |
| 2 | 98 s | pass | pass | 3/10 | 9/10 | 4.5 / 3.8 ms |
| 3 | 280 s | pass | pass | 6/10 | 7/10 | 3.3 / 3.8 ms |

- No assert or crash in any run.
- Peak heap use is about 58 kB (min-ever free 147 kB of 200 kB).
- Ping losses line up with asynchronous PAN advertisement/configuration sweeps
  (see [Known gaps](#known-gaps--todo)). Earlier runs gave 2–9 of 10.
- The Enh-ACK latency on the host includes Linux thread scheduling. It says
  nothing about RAIL timing.

## On-hardware test procedure (two kits: BRD4271A on BRD4001A, or BRD4270B on BRD4002A)

This follows GENERICITY_PLAN.md §5.10.

**Console.** The console is the kit VCOM (`/dev/ttyACM*`, **115200 8N1, no flow
control**). Use `picocom -b 115200 /dev/ttyACM0`, or `tests/hw/console.py`,
which timestamps every line on the host and forwards commands from a FIFO.

**Log format.**

- Every trace line is prefixed with milliseconds since boot.
- A one-line status (`== BR|RN <EUI-64> up <s> ready=<0|1> ... heap free ...`)
  is printed every 30 s and on `ARM_NWK_BOOTSTRAP_READY`.
- A crash is captured and printed at the next boot as `!! previous boot: FAULT
  …` with registers and the code addresses found on the stack; decode them with
  `arm-none-eabi-addr2line -f -p -e build/fw/wisun_<role>.elf <addr>`.

**Automation.** `tests/hw/run_hw.sh <workdir>` runs one cold boot of steps 2–7.
It resets the BR, then the RN, waits for the join and clears the statistics.
It then runs ping and UDP both ways and prints PASS/FAIL. Kit serial numbers and
ttys come from `BR_SN`, `BR_TTY`, `RN_SN` and `RN_TTY`.

1. **Flash and open both consoles.** Mass erase first. Check the first lines:
   - `nanostack-efr32fg25-freertos BR starting, RAIL x.y.z`;
   - EU: `PHY config ok: ch0 863100000 Hz, spacing 100000 Hz, 50000 bps, 69 channels`
     (NA: `ch0 902200000 Hz, spacing 200000 Hz, … 129 channels`).
     If instead you see "does not match the radio config", the stack PHY and
     `rail_config.c` disagree: stop.
   - No warning about RAIL IRQ priorities.
2. **Power the BR.** Expect:
   - `BBR started`;
   - `Border router start network`;
   - `fhss Configuration set ... UC CF: 2, BC CF: 2` (DH1CF);
   - `Routing ready`;
   - `network event on if 1: ARM_NWK_BOOTSTRAP_READY`;
   - a few seconds later, `Send PAN advertisement` and `Send PAN configuration`.

   `status` shows `join_state=5`, the PAN ID, `ws0 addr fd12:3456::<BR IID>`,
   `bh0 addr fd12:3456::1615:16ff:fe17:1819` and the BBR DODAG ID.
3. **Power the RN.** Expect, in order:
   - `Send PAN advertisement Solicit` (repeated);
   - `selected parent:<BR EUI-64>`;
   - `authentication start`;
   - `EAP-TLS init`, `EAP-TLS start`, …, `EAP-TLS finished`, with **no**
     `handshake fatal error` and no `drbg seed fail`;
   - 4WH/GKH key messages (`wspc`/`wsps` groups);
   - `learn network configuration`;
   - DAD on the GUA;
   - `network event on if 1: ARM_NWK_BOOTSTRAP_READY`.

   Target: under 5 min. Hardware (EU) took 118–144 s; the host twin (NA) took 68–280 s.
4. **Verify the join.**
   - Authentication: the lines above. The BR logs the EAP-TLS server side
     (`eapa`/`wspa` groups).
   - DHCPv6 address: on the RN, `status` lists `ws0 addr fd12:3456::…`.
   - RPL parent: on the RN, `status` shows `parent=fe80::<BR IID>`.
   - On the BR, `nodes` lists `node fd12:3456::<RN IID> parent fd12:3456::<BR IID>`.
5. **Ping.**
   - On the RN: `ping <BR ws0 GUA> 10`. On the BR: `ping <RN GUA> 10`.
   - Each run prints `n bytes from …` lines and a summary.
   - Pass: ≥ 9/10 replies **outside** async sweep windows. Each window is a
     `Send PAN advertisement` or `Send PAN configuration` trace on either node,
     followed by transmissions on every channel: about 1 s on EU (69 channels,
     ~13 ms each), 2–3 s on NA (129). Repeat the ping if a sweep overlapped.
6. **UDP.**
   - On the RN: `udp <BR GUA> hello`. The BR prints
     `udp rx from [<RN GUA>]:1234 … hello`.
   - The RN then prints `udp rx … ack:hello`.
   - Repeat from the BR to the RN.
7. **Radio health.** Run `radio clear` after the join (EAP-TLS ECC blocks the
   stack task for up to 0.9 s and dominates the maxima), wait, then run
   `status -v` on both nodes. Look at:
   - `rx_crc`, `cca_busy`, `missed`, `late`, `fail`, `sched_refused`;
   - `ack_lat_max`: end of a received frame to the start of our Enh-ACK. The
     MAC adds 1 ms on purpose, and the peer waits about 21 ms. It must stay
     under about 5 ms; if not, go to Phase B (MAC context, GENERICITY_PLAN.md §2.3);
   - `prepare_late_max`;
   - `timer_late_max`;
   - `trace_dropped`.

   `tasks` gives stack headroom if the SDK's FreeRTOSConfig enables
   `configUSE_TRACE_FACILITY`; otherwise only the stack task's own headroom is
   shown.
8. **Three cold boots.** Reset or power-cycle both boards (BR first) and repeat
   steps 3–6, three times. No persistence is implemented, so every boot is a full
   join with fresh keys.
9. **Robustness (optional).**
   - Reset the RN: it rejoins.
   - Reset the BR: the RN detects the loss and rejoins the new PAN.
   - Run 1 h: `heap` "min-ever" stays stable, `failed 0`.

A sniffer (third board with the RAIL sniffer, or Wi-SUN-PK6016A) can decrypt
the traffic: the BR forces all four GTKs to zero, like `examples/wsbrd.conf`.

## Hardware results (BRD4271A, EU, 2026-10-23)

**Setup.**

- Two BRD4271A Rev A06 on BRD4001A Rev A02, side by side on a desk. The RSSI of
  the peer is −13 dBm.
- TX power fixed at +10 dBm (`RAIL_PHY_TX_POWER_FIXED_DDBM`).
- Wi-SUN EU, operating class 1, mode 1a, network size small, 69 channels.
- Final firmware: commit `076fabc`.
- **Cold boot** means `commander device reset` of the BR, then the RN 3 s later:
  a pin reset, with RAM lost and no persistence, so every boot is a full join
  with fresh keys.
- Statistics were cleared once the RN had joined, then read 120 s later.
- Curated logs are in `tests/hw_logs/2026-10-23_brd4271a_eu/`.

The RN milestones are RN uptime from `selected parent`, `authentication
success` and `ARM_NWK_BOOTSTRAP_READY`.

- `sched_refused` was 0–4 per window, and every such frame was then sent

**Ping.** Ping losses (0–40 %) line up with asynchronous PAN
advertisement/configuration sweeps over 69 channels (about 1 s each). UDP
and every check before the ping were clean on all boots.

**Enh-ACK turnaround.**

- Measured from the estimated end of the received frame to the start of our
  Enh-ACK: **1.4–2.3 ms**.
- The MAC adds 1 ms on purpose, so the radio driver and port add 0.4–1.3 ms.
  The peer waits about 21 ms.
- `prepare_late_max` stayed at 160–200 µs.

**Timer lateness.**

- The 91 ms seen in the first single-board run is the RAIL calibration
  (`cal=1`) at start-up.
- During the join, the maxima are **0.73 s (BR) and 0.89 s (RN)**: EAP-TLS ECC
  (X.509 verification, ECDHE/ECDSA in mbedTLS software) blocks the single stack
  task. Join still works, because the MAC retries.
- After the statistics reset: 1.2–1.5 ms.

**FHSS drift compensation.** The RN's `synch to parent` trace (DEBUG, `trace 5
fhss`) reports a drift of 0–1 ms over 66–111 s between the two crystals
(≤ ~15 ppm; the trace has 1 ms resolution). Compensation is 0–10 ns per ms,
so there is real but small drift.

On the target the compensation is applied. It is compiled out on Linux
(`rcp/fhss/fhss_ws.c:1176`), so the emulator and the host twin never apply it.

**Resources.**

- Heap peak 46 kB on the BR and 40 kB on the RN; 0 failed allocations.
- Minimum free stack: `ns_stack` about 5.4 kB of 8 kB, `log_tx` 0.8 kB,
  `IDLE` 1.1 kB, `Tmr Svc` 0.5 kB.

### Hardware-only bugs found and fixed

1. **BR hard fault ~20 s after an RN authenticated** (commit `fedc8a7`).
   - Crash: BusFault, NULL read in `memchr()`.
   - Call chain: `ws_pae_auth_fast_timer` → `ws_pae_key_storage_supp_write`
     → `ws_pae_key_storage_trace` → `snprintf`; decoded crash in
     `tests/hw_logs/…/crash_newlib_nano_printf_int64.txt`.
   - Cause: newlib-nano's printf has no 64-bit integer formats. The stack
     traces `int64` values with `PRIi64`/`PRIu64`, so nano read the wrong
     varargs and the next `%s` got a NULL pointer.
   - Fix: link the full newlib (+18 kB flash).
   - The host twin (glibc) could not show it. The same cause printed
     `stored time: lu` in NVM traces.
2. **Up to half of the frames failed their first transmission** (commit `076fabc`).
   - `RAIL_StartScheduledCcaCsmaTx()` returns `SL_STATUS_INVALID_PARAMETER`
     when the start time is only ~260 µs ahead. The driver reported
     `CCA_FAIL`, so the MAC retried: before the fix, `fail` was 241–702 per
     2-minute window.
   - Fix: schedule only ≥ 400 µs ahead, prepare 800 µs before, and start
     immediately if RAIL refuses. Now `fail=0`.
3. **Crashes were invisible**: the BR just went silent. Commit `b42666d`
   added the `.noinit` crash record described in the
   [test procedure](#on-hardware-test-procedure-two-kits-brd4271a-on-brd4001a-or-brd4270b-on-brd4002a).
4. **Join stalled in about 1 boot in 15** (workspace HW9, 2026-10-27; design
   note 11).
   - Symptom: the RN never received a long frame, for example the BR's
     614-byte EAP-TLS frame, through all MAC retries.
   - Cause: the driver restarted RX on the new channel when FHSS changed
     channel in the middle of a reception, which aborts the frame.
   - Fix: `RAIL_PHY_HOP_DEFER`.
   - Evidence: [tests/hw_logs/2026-10-27_hw9_hop_during_rx](tests/hw_logs/2026-10-27_hw9_hop_during_rx/README.md).
     Without the fix: 2 stalls in 30 boots, and hundreds of frames cut. With
     it: 0 in 30, and no frame cut.

## FAN 1.1 LFN on the kits (GS8 stage 6, 2026-10-29)

**Images.** `wisun_lfn` is the router program started as a Wi-SUN FAN 1.1 Limited Function Node (`APP_ROLE_LFN`: `NET_6LOWPAN_HOST`, FAN 1.1, the LFN settings' defaults of the stack's `docs/LFN_STACK.md` §5). `FW_LFN_PARENT=ON` builds the border router with FAN 1.1 and LFN parenting, and a MAC key table of 7 entries (4 GTKs, 3 LGTKs). Every preset builds `wisun_lfn`; the parent needs its own build directory:

```bash
cmake --preset fw-mode3 -B build/fw-lfn -DFW_LFN_PARENT=ON
cmake --build build/fw-lfn --target wisun_br wisun_lfn
```

**What the LFN image does differently.**
- **EM2 between its windows (HW8 H3).** It does not hold EM1 (the FFN images do, `apps/common/node.c`), and `rail_phy_sleep_init()` configures RAIL's timer synchronisation and its power-manager integration: RAIL keeps its timebase across EM2 and wakes the chip before its next timer, so every port timer (RAIL multitimers) keeps working. FreeRTOS tickless idle lets the power manager enter EM2 whenever the radio is idle. The VCOM UART no longer holds EM1 to keep its receiver on (`SL_IOSTREAM_EUSART_VCOM_RESTRICT_ENERGY_MODE_TO_ALLOW_RECEPTION` 0, set by `tools/sdk_generate.sh`); the FFN images hold EM1 anyway. The LFN's console therefore reads input only while it is awake.
- **Quiet console.** No periodic status print, and traces at ERROR from `APP_LFN_QUIET_AFTER_S` (30 s) after the join: INFO traces, and some inherited WARN traces on every frame, would keep the UART and the CPU busy.
- **Radio driver (H1, H2).** `PHY_EXTENSION_READ_RX_ACTIVE` (a frame is being received: the MAC keeps a window open until it ends) and `PHY_EXTENSION_SET_BACKOFF_RX_OFF` (the radio idles from the TX request to the scheduled CCA and TX). Windows open and close through the MAC's state control (RX on, idle); a scheduled TX starts from idle, and RAIL returns to RX after it for the ACK.
- **Port.** `eventOS_callback_timer_start_usec()` (`NS_PORT_TIMER_USEC`): the event loop's idle-tick skipping lands its tick exactly on the 10 ms grid.
- **Test tools.** `ping <ipv6> [count] [size] [interval ms]` counts a reply to any request of the series, and waits 12 s after the last one: a reply from an LFN waits for its listen window.

**Results** (kit 440235509 as the LFN, AEM; kit 440240046 as the border router; EU mode 3, +10 dBm, the boards side by side at −16 dBm; LFN settings' defaults: listen interval 5 s after the parent's LTO, LFN broadcast slots every 10 s, a sync frame every 50 s):
- The LFN joins in 32–74 s from its reset (4 boots) (discovery window, parent chosen, EAP-TLS, LGTK, LPCS/LPC, DHCPv6, address registration); no fault in 4 boots once the memory errors below were fixed.
- UDP both ways (border router → LFN, and the LFN's acknowledgement back).
- **Idle current 24.9–26.9 µA** (AEM, 18 windows of 60 s in 3 boots). The emulator gives 24.0–24.7 µA for the same settings (`mesh-emulator-orchestrator/docs/POWER_MODEL.md` §17). Silicon Labs' LFN drew 49 µA on the same kit with its Test profile, whose intervals are the same (root repo, `HW5_BlackBox_Phase1_Results.md`).
- Pings from the border router, one request every 6 s: 10 of 10 answered, round trips 0.17–4.4 s (the wait for the LFN's next 5 s window; Silicon Labs' LFN: 0.45–5.1 s). With one request per second, replies came back 3.9–15.8 s later and 6 of 10 were not back after the grace: the parent sends an LFN at most one frame per listen interval, as Silicon Labs' parent does.

**Found on the way.** The first image faulted during EAPOL (an unaligned access in SHA-1, then a bus fault in the MAC's IE copy). Both were heap corruption from a 7-byte overflow in the stack's 4-way handshake message 2 for LFNs; AddressSanitizer in the emulator found it and a DHCPv6 relay stack-scope error (the stack's `docs/LFN_STACK.md` §10).

## Design notes

- **Execution model (Phase A).** One stack task (`ns_stack`, priority
  `configMAX_PRIORITIES-2`, 8 kB) runs `ns_port_run()`. RAIL and multitimer ISRs
  only record events or copy RX frames, then notify it. The driver bottom half,
  timer callbacks, FHSS callbacks, the event loop and the CLI all run in that
  task. A low-priority `log_tx` task drains the trace ring to the VCOM.
- **Run-loop wait.** The stack task blocks until a notification (ISR, timer
  expiry, CLI). `FW_RUNLOOP_SAFETY_MS` (CMake, default 0 = no limit) adds a
  timeout that only catches a missed notification. It was 100 ms until
  idle-tick skipping was checked on the boards (2026-10-28, above): with and
  without it, the same wakes, timers and joins.
- **Init sequence.** GENERICITY_PLAN.md §3.3 (`apps/common/node.c`), in this order:
  1. `rail_phy_hw_init()` (RAIL timebase);
  2. `ns_port_init()`;
  3. `eventOS_scheduler_init()`;
  4. `rail_phy_register(EUI-64 from DEVINFO)`;
  5. `ns_sw_mac_create(…, {32, 4, 1, 3})`;
  6. `net_init_core()`;
  7. `arm_nwk_interface_lowpan_init()`;
  8. [BR: `bh0`];
  9. the tasklet. It runs the `wsbr.c`/`wsrouter.c` configuration with
     `ws_management_node_init(…, &ns_port_fhss_timer)`.
- **Timebase.** `RAIL_GetTime()` µs for everything: callback timers, FHSS
  timers, PHY timestamps, `GET_TIMESTAMP`. Timers are RAIL multitimers; one
  `RAIL_MultiTimer_t` per Nanostack timer.
- **Radio frame format.**
  - RAIL 802.15.4 mode, promiscuous, auto-ACK off. The MAC builds the Enh-ACKs.
  - `RAIL_IEEE802154_G_OPTION_GB868`. The driver writes the 2-byte SUN PHR
    with **FCS type 4 bytes** and **data whitening on**
    (`RAIL_PHY_FCS_LEN`, `RAIL_PHY_WHITENING`); the radio adds and checks the FCS.
  - RAIL channel = Wi-SUN channel + offset. The generated configs number the
    EU/1a channels 256–324 and the NA/1b channels 512–640. The driver reads
    the offset, ch0 frequency, spacing and channel count from
    `channelConfigs[]`; the data rate and modulation index come from
    `FW_REGION`. Interoperation between two boards with this frame format
    (4-byte FCS, whitening) was verified on EU hardware.
- **TX timing.**
  - The prepare step (`CCA_PREPARE` callback + FIFO load) runs 800 µs before
    the MAC's absolute TX time.
  - CCA+TX is then started with `RAIL_StartScheduledCcaCsmaTx`: single
    160 µs CCA, no RAIL backoff.
  - The TX is sent immediately when it is already late (< 400 µs ahead) or
    when RAIL refuses the scheduled start.
- **Deviations from GENERICITY_PLAN.md (and why).**
  1. **Entropy.** The plan's `MBEDTLS_NO_PLATFORM_ENTROPY` alone breaks TLS.
     The stack registers its entropy source as WEAK, so `ctr_drbg_seed` fails.
     The SE TRNG is now a STRONG source via `MBEDTLS_ENTROPY_HARDWARE_ALT` +
     `mbedtls_hardware_poll()` (found with the host twin).
  2. **No `CCA_OK` on the `PHY_TX_ALLOWED` path**, only on `PHY_RESTART_CSMA`. This follows the emulator's
     reference driver: the MAC's `CCA_OK` handling tells FHSS the TX is over.
  3. **No submodule; the stack is built through its own CMake.**
     `cmake/nanostack.cmake` calls `add_subdirectory(NANOSTACK_DIR)` with
     `NANOSTACK_PORT=ns_port_freertos`, gives the stack this build's mbedTLS as
     `MbedTLS::*` aliases, and builds the MAC with
     `nanostack_add_rcp_library(... INPROCESS)`, which leaves out the duplicate
     `rcp/mac/rf_driver_storage.c` (D15). Until GENERICITY_PLAN.md step S3 this
     repo read the source lists out of the stack's `CMakeLists.txt` and had its
     own copies of the stack's `common/*.h` headers and `rand_*` helpers.
  4. **No file system.** The stack is built with `NANOSTACK_FILE_NO_STDIO`, so
     `ns_file_system.c` has no stdio fallback (before S3: link wraps onto
     failing stubs). The stack's root path stays NULL: storage is disabled,
     RAM-only first step (D9/D10).
  5. **Radio profile.** The SDK ships the NA single-PHY radio config as a FAN
     1.1-profile PHY (`…Plan1_2FSK_1b_NA`, ChanPlan 1). Its PHY parameters are
     the FAN 1.0 NA class 1 / mode 1b ones (902.2 MHz, 200 kHz, 129 ch,
     50 kbit/s, h = 1); the driver checks them against the stack's at
     `SET_RF_CONFIGURATION`.
  6. **Power.** An EM1 requirement is held permanently: always-on FFN, RX is
     continuous.
  7. **`sl_main`.** The SDK's start-up framework (`sl_main`) owns `main()`:
     `apps/common/node.c` `main()` runs in its start task.
  8. **Full newlib, not newlib-nano**, for the stack's 64-bit printf formats
     (see [Hardware results](#hardware-results-brd4271a-eu-2026-10-23)).
  9. **Region.** The coordinator chose Wi-SUN EU class 1 / mode 1a on BRD4271A
     for the bench: the boards are matched for 868 MHz only, and the bench is
     in Europe, where 902–928 MHz overlaps GSM-900. NA/BRD4270B stays as a
     build variant.
  10. **TX watchdog** (found 2026-10-23/26). RAIL sometimes accepts a scheduled
     CCA+TX and then never reports it. This happens when the stack's FHSS
     broadcast-slot handler, which runs in a critical section of up to about
     600 µs (`rcp/fhss/fhss_ws.c:312-429`), masks the RAIL interrupts across
     the scheduled start. The driver used to wait for that TX forever: the
     border router stopped transmitting in 6 of 14 boots of the first build on
     the S3 stack, and 0 of 11 of the build before. `rail_phy.c` now arms the
     prepare timer, which is idle during a TX, as a deadline (start + air time
     + 20 ms). On expiry it idles the radio, counts `tx_lost` (shown by
     `status -v`) and reports `CCA_FAIL`, so the MAC moves on or retries. Seen
     firing once on hardware: the border router transmitted again 25 ms later.
     In addition, a poll hook keeps the TRNG pool at least half full outside
     critical sections. The stack's `rand_*` helpers draw twice the bytes of
     this repo's old copies, which doubled the blocking Secure Engine refills
     inside that handler. The stack has since shortened those critical sections
     (GS6, 2026-10-26: about 600 µs down to 170–250 µs, no random draw
     inside); the watchdog stays as protection against any lost RAIL event.
  11. **No channel change during a reception** (`RAIL_PHY_HOP_DEFER`, default 1;
     HW9, 2026-10-27).
     - Why: `RAIL_StartRx()` on another channel aborts the frame being
       received. The sender picks the receiver's channel once, when the
       transmission starts (`rcp/fhss/fhss_ws.c:727`), so the receiver must
       stay on that channel until the frame ends.
     - Before the fix, the driver switched at once. A boot whose hop timing
       sat unluckily against the BR's TX slots lost every retry of a long
       frame.
     - Now: if RAIL is receiving a frame (`RAIL_RF_STATE_RX_ACTIVE`) when
       `PHY_EXTENSION_SET_CHANNEL` arrives, the driver records the channel,
       returns 0 and keeps receiving. The bottom half switches when the frame
       ends, or after 400 ms if the reception hangs.
     - The Enh-ACK goes out on the channel of the frame it answers, because
       the sender waits there.
     - It returns 0 rather than -1 on purpose. On -1, `mac_mlme_rf_channel_change()`
       (`rcp/mac/ieee802154/mac_mlme.c:1020-1042`) keeps the old `mac_channel`
       and nobody retries. A later request for that old channel is then
       skipped, and the radio stays on the wrong channel.
     - Counters (`status -v`): `rx_hop_abort` (with the option off),
       `rx_hop_deferred`, `rx_hop_defer_max_us`, `ack_on_rx_channel`. On the
       bench the longest deferral was 59 ms.

## Known gaps / TODO

- **Verified on hardware (EU, two nodes)**, see
  [Hardware results](#hardware-results-brd4271a-eu-2026-10-23):
  - RAIL init and the radio config;
  - PHR, FCS and whitening between boards;
  - scheduled TX, CCA, Enh-ACK timing, FHSS hopping and synchronisation;
  - EAP-TLS with the SE TRNG, DHCPv6, RPL, ping, UDP;
  - IRQ priorities (no boot warning), stack sizes, VCOM.
- **LFN (FAN 1.1):** see [FAN 1.1 LFN on the kits](#fan-11-lfn-on-the-kits-gs8-stage-6-2026-10-29). Not done: our LFN against Silicon Labs' parent and our parent against Silicon Labs' LFN (black-box phases 2–3, which need the interoperability IEs LCP/FLUS); long runs; the LFN's console in EM2. An LFN under a router runs on three kits, see [An LFN under a router on the kits](#an-lfn-under-a-router-on-the-kits-2026-10-30).
- **Still unverified:**
  - the NA/BRD4270B variant on hardware;
  - more than two nodes or multi-hop;
  - long runs (only about 5 min per boot);
  - RN or BR loss and rejoin;
  - CCA behaviour against real interference; CCA thresholds and TX power
    calibration;
  - range: the boards were next to each other at −13 dBm, and nothing checked
    receiver saturation or weak links;
  - power consumption.
- **Stack task blocked by ECC.** EAP-TLS ECC blocks the single stack task for up
  to 0.73 s (BR) and 0.89 s (RN) during each join. The MAC (ACKs, FHSS)
  stalls meanwhile, but join still works. Options:
  - Phase B (a higher-priority MAC context);
  - restartable X.509 verification;
  - SE-accelerated ECC (needs the mbedTLS 3.6/PSA path).
- **Async sweeps.** Every PAN advertisement, configuration or solicit is sent
  on all channels: 69 on EU (~1 s per sweep), 129 on NA (2–3 s). Several are
  sent per minute after a join, and unicast traffic is lost during sweeps.
  - Ping loss: 0–40 % on hardware (EU), 20–80 % in the host twin (NA).
  - This is protocol behaviour, not a driver bug.
  `APP_WS_CHAN_FIRST/LAST` (channel mask) was meant to shorten sweeps, but with
  a 16-channel mask the twin RN never got its unicast EAPOL acknowledged
  ("channels: BC 129 UC 16"). Experimental; to investigate in the stack.
- **No persistence** (NVM3 `ns_file_*` callbacks: TODO). Keys and frame counters
  are lost on reboot, and every boot is a full join. A router reset while its
  border router keeps running does not rejoin (seen on the three kits): it
  restarts its frame counter at 0 under the same GTK, and the border router,
  which keeps its neighbour entry, most probably rejects its secured frames
  as replays (`MLME_COUNTER_ERROR`); its DHCPv6 requests got no reply for
  18 min.
- **No real backhaul** (null `bh0`). SLIP-over-UART is Phase 2.
- **Phase B** (higher-priority MAC context) is not implemented. Measure
  `ack_lat_max` first.
- **MAC traces.** Silicon Labs/HEIG debug traces in the MAC (`mMCp`/`mPDs` at
  INFO/WARN, every frame) are compiled in and flood the console at trace
  level ≥ 3. The trace ring drops whole lines when full (`trace_dropped`).
  Use `trace 2` on the bench if needed.
- **Heap.** 200 kB for both images (plan: RN 128 kB). About 252 kB of RAM is
  unused and can go to the heap for a BR with many joins.
- **`configASSERT` is a no-op.** It maps to `EFM_ASSERT`, which is active only
  with `DEBUG_EFM`.
- The fake RAIL does not model RAIL's TX_ABORTED versus TX_BLOCKED, timing
  jitter of a real radio, or RSSI/LQI.
- **mbedTLS 3.0.0 is old.** The SDK's 3.6 (PSA) is the product path
  (GENERICITY_PLAN.md §7.2).
- **Stack-side improvements** proposed earlier are now in the stack: [docs/stack-patches](docs/stack-patches/README.md).
